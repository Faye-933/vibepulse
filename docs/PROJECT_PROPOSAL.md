# VibePulse 项目企划书

> 版本：1.0-draft  
> 项目周期：30 天（每天约 6 小时）  
> 目标平台：Raspberry Pi 4B / Linux  
> 当前状态：学习与实现阶段；树莓派尚未到货，硬件链路和性能指标均待验证。

## 1. 项目概述

VibePulse 是一个基于 C++ 和 Linux 的嵌入式实时交互项目。系统通过 MAX30102 获取手指 PPG（光电容积脉搏波）样本，分析红外信号并估算心率（BPM），再根据心率趋势或区间调整音乐风格，形成“生理信号采集—分析—控制—音乐反馈”的闭环。

本项目的核心目标是亲自实现并理解事件驱动采集与实时任务处理。音乐反馈是完整应用场景的一部分；开发顺序上先建立可靠的采集和 BPM 估算，再连接音乐控制，避免多个问题同时出现而难以定位。

项目是学习和工程实践原型，不是医疗设备，不用于诊断或治疗，也不承诺通过音乐改变用户生理状态。

## 2. 项目目标

1. 在 Raspberry Pi 4B 上读取 MAX30102 的 FIFO 样本。
2. 使用 GPIO 的 INT/DRDY 边沿事件唤醒采集任务，避免通过循环反复检查 GPIO 或无数据读取 FIFO。
3. 从 PPG 样本中检测脉搏峰值，按相邻峰值时间间隔估算 BPM，并处理无手指、噪声和异常跳变。
4. 将估算结果映射为简单、可解释的音乐反馈，例如舒缓、中性、活力三个音乐状态，并通过平滑淡变切换。
5. 逐步理解 Linux 线程、阻塞事件等待、线程优先级及实时性测量；所有实时性结论均以实际测量为依据。
6. 整理源码、运行步骤、测试结果和设计说明，使项目能够复现并用于技术交流。

## 3. 用户与使用场景

### 目标使用场景

用户将手指放在 MAX30102 传感器上，程序持续采集 PPG 信号并估算心率。心率估算稳定后，控制模块将其映射到音乐状态；当状态满足持续时间和切换条件时，播放器平滑切换到对应风格的音乐。

### 项目主要受众

- 项目作者：通过完整实现学习 C++、Linux、I2C、GPIO 事件、线程和基础实时系统实践。
- 技术面试官或评审者：能够检查模块边界、故障处理、测试设计和性能测量，并就实现取舍进行讨论。

## 4. 系统工作原理

MAX30102 输出红光和红外光强度样本，不直接输出心率或 BPM。程序从红外 PPG 波形中识别连续脉搏峰值；若峰间隔为 `T` 秒，则瞬时心率估算为 `60 / T` BPM。滤波、有效范围判断和时间平滑用于减少噪声引起的误检与抖动。

GPIO INT/DRDY 与心跳峰值是不同事件：DRDY 表示传感器 FIFO 中有新样本可读，峰值则是算法从一段 PPG 波形中检测出的脉搏特征。采集事件发生频率通常远高于心跳频率。

音乐 BPM 与心率 BPM 使用相同单位，但表示不同对象。第一阶段采用稳健易解释的策略：按平滑心率区间选择音乐风格；加入迟滞和持续时间确认，防止阈值附近频繁切换。连续调整音乐速度属于后续探索，不要求音乐 BPM 等于心率 BPM。

## 5. 计划架构

```text
MAX30102
   │ I2C FIFO + INT/DRDY 边沿
   ▼
采集任务 ── 样本队列/回调 ──► 心率分析器
                                  │ BPM、手指状态
                                  ▼
                             音乐控制器
                                  │ 目标风格/切换事件
                                  ▼
                             音频播放模块

状态日志、CSV、延迟统计：旁路记录各阶段，不阻塞实时采集/音频路径
```

初期可在一个采集线程内完成“等待边沿—读取 FIFO”，并将样本交给算法；先保证行为正确，再根据测量结果拆分分析任务。线程优先级不是第一步：先理解普通调度、阻塞等待和延迟来源，再尝试实时调度并对比数据。

建议模块边界：

- **设备采集层**：I2C 初始化、MAX30102 配置、FIFO 读取、GPIO 边沿等待及硬件错误计数。
- **心率分析层**：滤波、手指检测、峰值检测、BPM 计算和平滑；不依赖 GPIO/I2C。
- **音乐控制层**：将有效且稳定的 BPM 映射到音乐状态，管理迟滞、确认时间和切换策略。
- **音频输出层**：封装实际播放后端，执行播放和淡入淡出；不在采集线程中执行耗时音频操作。
- **观测与应用层**：负责组装模块、生命周期、状态输出、CSV 与延迟记录。

## 6. 功能范围

### 本周期核心范围

- Raspberry Pi 4B 上 MAX30102 基本通信和样本采集。
- GPIO INT/DRDY 事件驱动 FIFO 读取。
- 错误、溢出、手指移开等状态可被发现并报告。
- 基础 PPG 处理和 BPM 估算；以录制样本或合成信号辅助调试。
- 依据心率状态进行舒缓/中性/活力音乐切换，并平滑过渡（硬件音频可用时）。
- 记录关键时间戳，观察采集和处理延迟；逐步尝试线程优先级。

### 暂不作为首要目标

- 医疗级心率或血氧精度、诊断和治疗用途。
- 机器学习、情绪识别、云服务、手机应用和图形界面。
- 实时相位声码器、复杂时间伸缩、音乐 BPM 精确跟随心率。
- 在没有测量依据时宣称达到硬实时或特定延迟指标。

## 7. 实时性学习与验证

项目中的“实时”首先指：事件发生后，系统能在可观察、可测量的时间内响应，并且不会因为主动轮询或慢速日志操作妨碍关键路径。Linux 上运行并不自动意味着硬实时；普通调度下的延迟也可能受系统负载影响。

分阶段验证：

1. **事件正确性**：INT 边沿能唤醒采集任务；无边沿时线程阻塞等待，不反复读 FIFO。
2. **采集完整性**：对比事件数、FIFO 样本数和错误/溢出计数，检查是否丢样。
3. **时间测量**：使用单调时钟记录边沿事件、读取完成、算法输出等阶段时间，统计分布而不只看平均值。
4. **调度探索**：在具备权限和稳定测试条件时，比较普通调度与实时优先级的观测结果；记录配置、负载和限制。
5. **端到端响应**：硬件和音频链路可用后，测量从采集到音乐控制生效的时间。目标值先作为待验证假设，不作为已完成结果。

每天包含一个底线任务和一个学习目标。硬件预计第 3 天到货；若到货时间变化，按实际情况顺延真机任务，先做代码阅读和离线处理。

| 阶段 | 天数 | 底线成果 | 学习重点 |
|---|---:|---|---|
| 建立认知 | 1–2 | 观察现有项目构建与运行，画出现有数据流 | CMake 构建、C++ 源码结构、PPG 与 BPM 概念 |
| 硬件与总线 | 3–7 | Pi 系统准备、启用 I2C、读取芯片 ID、配置 FIFO 并采样 | Linux 基础、I2C、寄存器、FIFO、传感器信号质量 |
| GPIO 事件采集 | 8–14 | 验证 INT 波形，实现边沿等待后读 FIFO，加入停止和错误处理，保存带时间戳数据 | GPIO 边沿、阻塞等待、线程生命周期、单调时钟、数据完整性 |
| BPM 分析 | 15–20 | 实现基础滤波、峰值检测、间隔换算、手指状态和实时 BPM 输出 | 滤波延迟、峰值检测、阈值迟滞、BPM 平滑与误差 |

每日约 6 小时可按“学习和阅读 1.5 小时、编码 3 小时、运行观察 1 小时、总结 0.5 小时”安排。底线任务优先；当天新知识要能用自己的话解释，并记录遇到的问题。

## 10. 风险与应对

| 风险 | 影响 | 应对方式 |
|---|---|---|
| 传感器接线或 INT 配置不正确 | 无法触发采集 | 先用芯片 ID 和逻辑分析仪逐步检查供电、I2C、INT 配置 |
| PPG 波形质量不佳 | BPM 误检 | 固定手指与传感器，检查原始波形；先保存数据再调算法 |
| 对 Linux 线程和实时调度不熟 | 设计容易变成照抄 | 先建立单线程事件等待，再逐步增加线程与调度实验 |
| Pi 音频设备或后端不可用 | 音乐实测受阻 | 将控制器与音频后端解耦，用模拟后端先验证切换行为 |
| 30 天内范围过大 | 核心链路未完成 | 优先级依次为事件采集、BPM、可测量性、音乐闭环、调度优化 |

## 11. 最终交付目标

30 天结束时，争取具备一条能解释和验证的端到端链路：MAX30102 的 GPIO 事件触发采集，程序从 PPG 估算 BPM，并将稳定的心率状态映射为音乐反馈；同时留有构建说明、测试/实测记录和未解决问题清单。

具体能否完成真实音乐播放、线程优先级对比和性能目标，取决于硬件、系统环境及实测结果。项目成果以实际可复现的证据为准，不把计划指标描述为已达到的性能。
